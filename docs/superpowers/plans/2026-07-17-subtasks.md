# Subtasks (ATLAS-2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Subtasks as first-class child issues under stories/tasks/bugs, with progress rollup on the parent — spec: `docs/superpowers/specs/2026-07-17-subtasks-design.md`.

**Architecture:** A subtask is an issue with `type='subtask'` and `parent_id` → a story/task/bug in the same project. `validateHierarchy` in `backend/routes/issues.js` is the single choke point for all hierarchy rules (3-level tree: epic → story/task/bug → subtask). `enrichIssue` carries generic parent join fields and subtask rollup counts so the UI needs no extra requests. Subtasks never appear on board/backlog; they live in the parent's detail sheet with a quick-add input.

**Tech Stack:** Express 5 + sql.js/MySQL backend (`backend/`), Vite + React 18 + TS + shadcn frontend (`frontend/src`), Jest + supertest tests (`backend/tests`).

## Global Constraints

- **No schema change** — `issues.type` CHECK already permits `'subtask'`; `parent_id` exists.
- Every validation failure returns 400 with a specific message (exact strings in Task 1).
- mysql2 returns SUM/COUNT aggregates as strings — coerce with `Number()` in API responses.
- The create-issue dialog does NOT offer the subtask type; quick-add in the parent sheet is the only creation path.
- Subtasks carry no `sprint_id` ever; epic rollups count direct children only (subtasks naturally excluded because their parent is not an epic).
- Work on branch `feature/subtasks`. Commit after every task. Frontend build output (`frontend/build/`) is committed to git (repo convention).
- Backend tests run from `backend/`: `npm test` (or `npm run test:backend`). Frontend typecheck+build: `cd frontend && npm run build`.
- **Never** start a dev server without checking `lsof -iTCP:3001` first — a stale `node server.js` owns the port and overwrites `backend/data.db` with stale state on any write.

// Hierarchy rules: a strict three-level tree. Epics take no parent and no sprint;
// stories/tasks/bugs may hang under an epic; subtasks must hang under a
// story/task/bug and follow their parent's sprint. Returns an error message or null.
const SUBTASK_PARENT_TYPES = ['story', 'task', 'bug'];

async function validateHierarchy(db, { id, projectId, type, parentId, sprintId }) {
  if (type === 'epic') {
    if (parentId) return 'An epic cannot have a parent';
    if (sprintId) return 'An epic cannot be assigned to a sprint';
  }
  if (type === 'subtask') {
    if (!parentId) return 'A subtask requires a parent issue';
    if (sprintId) return 'A subtask follows its parent sprint and cannot be assigned to one directly';
  }
  if (id) {
    // An issue keeps its children only while its type remains a valid parent for them.
    const kids = await queryOne(db,
      "SELECT COUNT(*) as total, SUM(CASE WHEN type = 'subtask' THEN 1 ELSE 0 END) as subtasks FROM issues WHERE parent_id = ?", [id]);
    const subtaskKids = Number(kids.subtasks || 0);
    const epicKids = Number(kids.total) - subtaskKids;
    if (epicKids > 0 && type !== 'epic') return 'Cannot change type: this epic still has child issues';
    if (subtaskKids > 0 && !SUBTASK_PARENT_TYPES.includes(type)) return 'Cannot change type: this issue still has subtasks';
  }
  if (parentId) {
    const parent = await queryOne(db, 'SELECT id, type, project_id FROM issues WHERE id = ?', [parentId]);
    if (!parent) return 'Parent issue not found';
    if (type === 'subtask') {
      if (!SUBTASK_PARENT_TYPES.includes(parent.type)) return 'A subtask parent must be a story, task, or bug';
    } else if (parent.type !== 'epic') {
      return 'Parent must be an epic';
    }
    if (parent.project_id !== projectId) return 'Parent must be in the same project';
  }
  return null;
}

export function SubtaskProgress({

      {done}/{total}
    </span>
  );
}
